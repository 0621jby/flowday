# 开发路线图

[索引](README.md) · [可执行任务与门槛](10-backlog.md)

本轮完成设计与路线图，第三轮需用户确认架构和开发顺序后才开始应用开发。工期假设2名全栈+兼职设计，约12–16周，含集成与修复缓冲；单人可能20–28周。不是交付承诺；日历授权、支付主体审批可能另增等待。

| 阶段 | 预计 | 目标与具体产物 | 数据库变更 | 退出标准/风险 |
|---|---|---|---|---|
| P0 产品验证与设计冻结 | 1–2周 | 补原PRD差异；15访谈；首发市场；原型；ADR；威胁模型 | 仅审查schema，无生产迁移 | 核心人群/闭环/价格实验明确；无真实需求则缩范围 |
| P1 平台与任务基础 | 2周 | 仓库、CI、认证、用户、任务、权限、错误监控、导出删除骨架 | profiles/preferences/goals/milestones/tasks/events/audit/idempotency | A01–A05；跨用户访问0成功；风险为RLS与认证缓存 |
| P2 计划与执行闭环 | 3周 | 时间库、排程、版本预览提交、计时、复盘、简单重复任务 | plans/revisions/items/blocks/execution/focus/reviews/series | A06–A11；5场景与DST通过；风险为状态一致性 |
| P3 有界Coach | 2周 | Prompt/adapter、受阻建议、审批执行、额度、通知策略 | runs/proposals/approvals/operations/usage/notifications/jobs/outbox | A12–A15；注入越权0；断开AI仍可完成闭环 |
| P4 商业化与封闭Beta | 2周 | 支付订阅、失败续费、取消、客服、30人试用、恢复演练 | subscriptions/payments/inbox/data_requests | A16–A20；支付乱序与备份恢复实测；不达留存先修产品 |
| P5 上线硬化 | 2–3周 | 无障碍、移动性能、负载、隐私、告警、灰度发布、运营手册 | 必要索引/保留期/聚合，不做破坏迁移 | A21–A24；无P0/P1缺陷；运营有人响应 |
| P6 增长后迭代 | 按证据 | 单向日历、画像、周计划、连接器 | connections/external_events/features/metrics | 有用户需求和留存证据，逐项评审，不承诺日期 |

关键依赖：身份/RLS → 任务事实 → 时间排程 → 执行记录 → AI建议/审批 → 商业化。支付模型可以设计并行，但不能在权益账本之前开收费。后台基础随P2搭骨架，在P3完善重试和死信。

灰度：内部测试→10人→30人→邀请制100人→公开；每阶段审查失败率、干预反感、成本和数据错误。可用 feature flag 关闭AI、自动提醒、支付新购；不能关闭用户读取和导出。数据库迁移先 staging 演练，应用回退保持兼容。

停止/转向条件：用户反复拒绝规划仪式、AI与规则版无收益差异、W4留存未达到预注册门槛、付费意愿不足时，优先减步骤/改人群，而不是继续增加功能。出现跨用户数据泄露、双重扣款、执行记录丢失则停止扩量并修复。
