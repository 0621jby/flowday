## 配置开发数据库与认证

1. 准备一个空白的 Supabase **开发项目**。本阶段无需添加付费服务。
2. 在该项目 SQL Editor 中执行 [202611190001_workspace.sql](../supabase/migrations/202611190001_workspace.sql) 全文。脚本自身带事务；失败会整体回滚。它是新项目基线，已经执行成功后不要再次执行。仓库中 `docs/sql/001-core-draft.sql` 是旧设计草案，不能与本迁移混用。
3. 在 Supabase Auth 中启用 Email/password，保持邮箱确认开启；最短密码设为 12 位，要求字母和数字，与应用注册校验一致。启用提供方的登录和注册频率限制。本实现把 429 反馈为稍后重试。
4. Site URL 填 `http://127.0.0.1:3100`，Redirect URLs 加入 `http://127.0.0.1:3100/auth/callback`。保持地址一致，不要在 localhost 与 127.0.0.1 之间切换。正式部署改为对应 HTTPS 域名。
5. 将 [.env.example](../.env.example) 复制为 `.env.local`，填写项目 URL 和 Publishable key；兼容旧 anon key。**不需要 service_role、sb_secret、数据库密码或 Supabase 管理令牌。不要把真实值提交到 Git，也无需把密钥发到聊天中。**

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLISHABLE_KEY
APP_ORIGIN=http://127.0.0.1:3100
```

6. 重新启动 `npm run dev`，打开上述地址。配置后首页要求登录。注册若需要邮箱确认，会提示查看邮件，不能把“注册请求成功”当成已登录。邮件链接须在发起注册的同一浏览器打开（PKCE）；也可完成邮箱验证后返回密码登录。
7. 正式部署应在构建和运行环境都配置这些变量。生产 Cookie 默认 Secure；若仅在本机用 `npm start` 验收 HTTP，额外设置 `FLOWDAY_ALLOW_LOCAL_HTTP=1`，该开关仅对 APP_ORIGIN 为本机地址生效。正式 HTTPS 环境删除此项。

只有两个 Supabase 变量都为空时使用本地模式；只配置一个或提供管理员密钥会报配置错误。云端不可用时不会自动切回本地、生成示例覆盖云数据，或显示连接成功。

## 体验与本地迁移

新云端账户为空，不自动写入示例任务。登录后进入“个人设置 → 你的云端账户”，可以新建任务/目标或迁移现有本地工作区。

迁移入口显示目标邮箱、任务/目标/时间块/复盘/执行记录数量，以及可展开的内容预览。文字、心情、涂鸦、偏好和进行中的专注会一起迁移。建议先下载原始 JSON 备份，核对数据确实属于当前账户，再勾选确认。

迁移规则：

- 仅允许导入从未修改的空白云端工作区（revision=0）。先迁移再创建云端数据。已有云端修改时不自动合并、不会直接覆盖；保留本地数据供后续手工合并。
- 相同内容按账户记录 SHA-256 摘要、导入版本与数量回执。重复请求只返回已有回执和最新云端内容，不重复创建，也不覆盖导入后的修改。
- 导入为单个数据库事务：写入和回执一起成功或一起回滚。客户端导入前再检查本地数据是否被其他标签页改动。
- 成功后服务端逐字段回读比对，统一日期格式及可选字段默认值。数量相同但内容不同不能通过完整性核对。
- **无论成功或失败，都不删除或改写 `flowday.workspace.v1` 原始数据。** 迁移后的本地副本不会继续同步回云端。已导入的识别依据是服务端回执，清除页面状态不会造成重复导入。
- 共享设备不会自动认定本地数据属于登录者；必须由当前用户核对。若要恢复失败，重新登录/重新同步后用同一份本地数据重试。保留的 JSON 可用于人工恢复，不提供自动覆盖已有云端账户的恢复按钮。

## 写入、权限与并发行为

浏览器通过同源 `/api/workspace` 请求，服务端核验 Supabase 用户身份、来源和请求绑定的账户 ID，再执行数据库函数。账户 ID 请求头只防止旧标签页在切换账户后误写；它不能代替身份认证。所有数据库调用携带当前用户 JWT，不使用管理员密钥。

数据采用规范化表；为复用 MVP 状态接口，第一阶段将工作区作为一次保存事务提交。每次提交锁定 `workspaces` 行，检查 expected revision，更新数据，增加 revision，再回读快照。客户端等数据库确认后才显示成功、关闭编辑框，期间防止重复提交。

冲突返回 409，不覆盖其他设备记录。保留当前表单草稿，点击设置中的“重新同步”读取最新数据；任务或复盘若已被修改会要求重新打开并人工合并。读取为一致快照，**当前使用主动读取和手动同步，没有实时推送或离线编辑队列**。

网络响应丢失时同一个 mutation ID 重试一次。两次均无法确认则停止继续写入，先重新同步判断实际提交结果，避免在不确定状态下继续创建。重试回执只覆盖最近一次普通保存；其后其他设备已提交时会返回冲突，不重放旧快照。本地导入回执独立持久化。

数据库所有业务表启用 RLS，只授予 authenticated 用户读取自己行的权限。直接 INSERT/UPDATE/DELETE 被撤销，写入仅通过函数；函数采用固定空 search_path、从 `auth.uid()` 取得 actor、锁行和约束验证。SECURITY DEFINER 函数不接受任意 user_id，公共快照函数不对外开放。AI/规则教练均不持有数据库访问凭据。

## 实际表结构

| 表 | 作用和关键约束 |
|---|---|
| auth.users / profiles | 提供方身份与应用用户；删除身份级联清理应用数据 |
| user_preferences | 称呼、每日可用时段、容量；检查范围及开始早于结束 |
| workspaces | 每用户唯一版本、最近 mutation/hash 与更新时间，事务串行点 |
| goals | 用户范围内 text ID、标题、说明、颜色、目标日期、稳定顺序 |
| tasks | 与用户/目标组合外键、分钟数/状态检查、完成时间一致性 |
| daily_plans | 用户+日期唯一；由任务安排日期生成的日计划，不复制任务事实 |
| schedule_blocks | 每任务一个时间块、与任务/日计划组合外键、分钟范围、锁定；函数检查重叠和任务状态 |
| schedule_history | 排程变化时记录版本和时间块快照 |
| execution_events | 完成/重开/专注事件，支持被删除任务的历史标识与专注秒数 |
| focus_sessions | 每用户最多一个进行中会话、引用自己的未完成任务 |
| daily_reviews | 每用户每天唯一的文字/心情/矢量涂鸦，限制内容大小 |
| local_imports | 每用户每内容摘要唯一，导入版本、数量与时间回执 |

保留原有 `g1/t1` 等 text ID，以 `(user_id,id)` 隔离，避免迁移时重建引用。目标关联、任务日期/状态、完成时间、排程日期和执行时间均有对应索引。数组顺序用 position 存储，避免迁移或刷新后无故重排。

任务删除后执行事件仍保留，因此历史 task_id 不设会级联删除历史的任务外键。账户删除由 auth.users → profiles → 所有业务表级联，已经测试；本阶段尚未开放自助删除账户界面。

日计划/时间块沿用 MVP 的本地日期和墙上分钟，不假装已支持跨时区转换。历史时间戳使用 timestamptz；专注起点使用 epoch 毫秒。完整 IANA 时区/DST 排程属于后续阶段，跨时区设备会使用各自浏览器的日期边界。

## 2026-11-19 编辑与删除入口修复

日历点击任务后可打开任务详情或确认删除，也可仅移出时间轴。删除任务会一并移除时间块，并保留历史执行记录；进行中的专注仍需先结束。目标卡片新增明确的编辑和删除按钮，支持修改名称、说明与目标日期。删除目标需确认，关联任务解除目标关系，保留日期、时间块和执行记录。所有更改仍经过原有本地/云端保存边界，保存成功后才关闭弹窗。新增两项浏览器回归测试验证取消删除、修改与删除后刷新，以及关联数据保留；现共 64 项逻辑/API/数据库测试与 7 项浏览器测试通过，生产构建通过。

## 目标删除确认流程调整

目标卡片只显示编辑入口；删除按钮移入编辑窗口。删除前可选择保留关联任务（默认）或同时删除全部关联任务（含已完成任务）及其时间块，均保留历史执行记录。确认窗口展示影响数量；返回编辑时保留未提交的草稿。有关联专注会话时，禁止连同任务一起删除，须先结束专注，仍可选择保留任务。关联处理与目标删除经同一次保存事务提交，无新增数据库迁移。64 项自动化测试、7 项浏览器测试及生产构建通过。
